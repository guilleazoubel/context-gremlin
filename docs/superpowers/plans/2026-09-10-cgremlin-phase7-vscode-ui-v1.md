# cgremlin Phase 7: VS Code UI v1 and its core additions — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the UI as a VS Code extension, and add to `cgremlin/core` every capability that UI needs and the engine cannot currently answer: a **source-generic** attention model with persisted per-item-ref acknowledgement and a core-computed `needsYou` (R22), a Server-Sent-Events stream over the existing Unix socket with an explicit, ordered, back-pressured fan-out (R21), an **expiring** human-turn claim that actually blocks the pipeline and cannot wedge it (R19, R20), a resume contract, an artifact listing with a core-chosen primary artifact, a redacted resolved-config read, direct development-session creation, and manual review from any PR URL (R23).

**Generality constraint (R18, binding).** The core attention model and the panel's view model are defined over a generic `Item = { source, ref, id, title, repoOrContext, attention, links }` with one `SourceAdapter` + one pure `derive*Reasons` per source, and acknowledgement keyed by `ItemRef`. v1 ships exactly two sources (`session`, `pr`); the roadmap adds Jira tickets + ticket comments and a Slack mentions inbox (spec §10), and each of those must be a new adapter + a `LIST_ORDER` entry, **not** a restructuring. Nothing Jira- or Slack-specific is implemented in this phase.

**Architecture:** Two streams that develop in parallel across four branches, then one integration task. **Stream A (core, three branches — see Parallelism):** the item-ref grammar, per-source pure reason derivers, the shared pure evaluator, an ack store and an adapter-composing `AttentionService`; a `SessionWatcher` port with a recursive-`fs.watch` adapter and a fake; an `EventRing` + `GET /events` SSE route with `Last-Event-ID` replay and R21's live fan-out; `session.agent.humanTurn` as an expiring claim with claim/release, an advisory pre-lock refusal **and** the authoritative refusal inside every stage's *locked* pre-run (R19), four stale-claim recovery paths (R20) and a reconciliation-tick skip; artifact listing + `pickPrimaryArtifact` + `GET /config`; `createDevelopmentSession` + `POST /sessions/developments`; `POST /reviews { prUrl }` reaching the already-tested-but-unreachable `ReviewSessionFactory.createFromPrUrl`. **Stream B (extension, new package `cgremlin/vscode`, branch `phase7-b`):** scaffold, socket client, SSE consumer, and four pure modules (view model, notification policy, managed-workspace planner, chat-command builder) developed against fixtures shaped by the spec, then the VS Code host wiring. **Convergence:** one integration task running the extension's client and mapping layer against a real engine on a temp socket with a fake `gh` on PATH, then docs.

**Tech Stack:** core — TypeScript, zod, vitest, `node:fs.watch`, `node:http` (no new dependencies). Extension — TypeScript, `tsc` (no bundler, R13), `@types/vscode`, vitest; **no runtime dependencies**; no `@vscode/test-electron` anywhere.

**Spec:** `cgremlin/core/docs/superpowers/specs/2026-09-10-cgremlin-phase7-vscode-ui-v1-design.md`. R1–R5 and R15–R18 are binding user decisions; **R19–R23 are binding supervisor rulings** and are already folded into every task below (R19 double refusal, R20 expiring claim, R21 SSE fan-out, R22 `needsYou`, R23 `POST /reviews` → 200 on an already-tracked PR). **R6–R14 were confirmed by the supervisor on 2026-09-10 and are binding.**

## Verified Ground Truth (2026-09-10, planner grounding pass)

**Platform facts I verified by running them on this machine (Node v24.18.0, darwin 25.6.0)**
- `fs.watch(dir, { recursive: true })` works and reports **relative** paths: writing `<dir>/s1/AGENT_STATE` produced `[["change","<dir-basename>"],["rename","s1"],["rename","s1/AGENT_STATE"]]`. So the adapter must keep only two-segment paths and discard the bare-basename and bare-dirname noise.
- SSE over a Unix-socket `http.Server` works: a client `http.request({ socketPath, path, headers: { 'Last-Event-ID': '7' } })` had `req.headers['last-event-id'] === '7'`, and received `id: 1\nevent: ping\ndata: {…}\n\n` as a single chunk.
- With that SSE connection still open, `server.closeAllConnections()` followed by `server.close(cb)` completed immediately — i.e. `serve()`'s existing shutdown path (`src/host/serve.ts:196-197`) does **not** hang on an open event stream.

**Engine facts the plan builds on (all read, not assumed)**
- `EngineEventMap` has six events and is documented "each in-process only" (`src/engine/events.ts:6-13`); `EngineEvents.emit` swallows subscriber throws (`:27-35`), so an SSE writer that throws cannot break the engine.
- `handleRequest` is a flat if-chain over `parts`/`method` ending in a 404, wrapped in one try/catch feeding `mapErrorToHttp` (`src/api/server.ts:347-547`). New routes are branches; the SSE branch must `return` before that fall-through and must never call `sendJson`.
- The comment at `src/api/server.ts:403-409` is explicit that `/transition`, `/run`, `/promote`, `/rereview`, `/retry`, `/approve-plan` must **not** be wrapped in `lock.withLock` at the route layer (KeyedLock is not re-entrant). `claim`/`release` therefore lock inside `PipelineService`, like `transition` does (`src/pipeline/pipeline-service.ts:116-118`).

Every stage already re-loads fresh state inside `runStageLocked`'s `preRun`: `runFindings` `:296-301`, `runPlan` `:336-350`, `runDevelop` `:436-441`, `runReview` `:479-492`, `runRereview` `:594-615`. A refusal that only happens inside the lock has already mutated the worktree the human is talking to the agent about. The advisory check goes first-after-the-mode-check: `:288-290` (findings), `:328-330` (plan), `:423-425` (develop), `:453-455` (review), `:529-531` (rereview — ahead of its `pr`/worktree reads *and* the git work).

- **Nothing starts an agent that was not explicitly asked for** (`docs/ARCHITECTURE.md:186-191`). Neither `AttentionService`, nor the event stream, nor `createDevelopmentSession` may call `runReview`/`runStage` (MG-A8, MG-A11).

- The extension has **zero runtime dependencies** and its pure modules never import `vscode` (MG-B1).
- `cgremlin/vscode` is a standalone package (there is no root pnpm workspace); it references the core only through the socket API and, in tests, through `../core/bin/cgremlin-core`.
- Branches, all off `mission-control-pr-orchestrator`: **one branch per parallel core agent** — `phase7-a1a3` (A1 then A3), `phase7-a4` (A4), `phase7-a2a5` (A2 then A5) — plus `phase7-b` for every extension task (B1→B2→B3). **Merge order, and what the supervisor resolves at each merge.** `phase7-a1a3` → then `phase7-a4` → then `phase7-a2a5` → then `phase7-b`; C1–C2 run on the merged base. Every core branch adds a separate branch to `handleRequest`'s flat if-chain and a separate wiring line to `buildEngine`, so the conflicts are textual, not semantic — but they are guaranteed, so the supervisor resolves them explicitly rather than letting an agent rebase onto a moving target. The touch points, by file:

- **`src/api/server.ts`** — all three core branches add routes: A1 `/attention` + the two ack aliases, A3 `/events` (whose branch must `return` before the 404 fall-through and must never call `sendJson`), A4 the three conversation routes, A2 `/sessions/:id/artifacts` + `/config`, A5 `/sessions/developments` + `/reviews`. Resolution: keep every branch, ordered by path specificity as the existing chain already is; verify the DoD `withLock` grep after each merge.
- **`src/api/http-errors.ts`** — A4 adds `HumanTurnInProgressError` → 409, A5b adds `InvalidPrUrlError` → 400. Resolution: both entries, and the default case's test stays green.
- **`src/host/build-engine.ts`** — A1 constructs the ack store, the two adapters and `AttentionService`; A3 constructs the `EventRing` and the `NodeSessionWatcher` and subscribes them; A4 passes `runnerKind` and `humanTurnTtlMs` into `PipelineConfig`; A2 passes `config` into `ApiServerDeps`. Resolution: all four, in that order.
- **`src/pipeline/pipeline-service.ts`** — A4 owns it (schema, the ten refusal sites, claim/release/conversation, the terminal clear) and A5a adds `createDevelopmentSession`. Resolution: A4 merges **first** so A5a lands on top of the final refusal wiring, and MG-A9's byte-identical header fixture is re-checked after the merge, not before.

Resolution: the two follow-up wirings are two lines each in a file the first merge already landed, which is why A1→A3 merges first and both placeholder assertions are replaced by the task that fills them.

Stream B never touches `cgremlin/core`, so `phase7-b` merges cleanly regardless of order among the core branches.

Rationale for the tiers: A1 introduces a new persisted state file and a new service that must provably take no session lock; A3 owns a long-lived HTTP response with an explicit replay→live handover and back-pressure policy (R21), a filesystem watcher and engine shutdown ordering; A4 modifies the file that documents the locking invariant, adds a second (advisory) refusal site per stage plus a claim lifecycle with four recovery paths (R19, R20), touches the two `StageRunner` sites that silently drop new `agent` fields, and touches the reconciliation tick — the highest-risk change in the phase; B3 is almost entirely un-unit-testable VS Code surface and carries the workspace-swap behaviour including the dirty-editor modal. A2, A5, B1 and B2 are additive, fully specified, and land behind explicit test lists — A5b in particular adds a route over a factory method that is already unit-tested.

**Every judgment call in this plan is decided, and each decision names its ruling.** The rulings that closed the last open ones are R19 (where the refusal goes: both places, and which one is authoritative), R20 (what happens to a claim nobody releases: it expires, and four paths clear it), R21 (how the SSE fan-out hands over, drops and cleans up), R22 (who computes "needs you": the core, once), R23 (`POST /reviews` on an already-tracked PR: 200, matching the other review route), plus the textual unifications — one `signature`, one `refresh` scope shape, one PR-ref formatter, no second artifact allow-list. Nothing below the task level is left to an executor's discretion; where two tasks must touch one file, the merge order and the resolution are written out above rather than delegated.
